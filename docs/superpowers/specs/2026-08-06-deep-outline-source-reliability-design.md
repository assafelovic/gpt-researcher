# 深度研究提纲与来源可靠性设计

## 背景

当前系统可以直接执行普通研究或 Deep Research，但用户无法在深度研究开始前查看和修改研究提纲；搜索或抓取失败时，流程也可能继续生成引用失效、来源不足甚至空白的报告。项目需要在一周内形成一个可演示、可测量、能够体现 Agent 规划与失败恢复能力的改进版本。

## 目标

1. 普通模式保持快速路径，不增加提纲确认步骤。
2. 深度模式先生成结构化提纲，等待用户确认或修改后再开始研究。
3. 普通模式使用 `qwen-plus`；深度模式使用 `qwen3.7-max` 负责提纲、研究规划和最终写作，网页摘要继续使用 `qwen-plus`。
4. 对研究来源执行规范化、去重和有效性验证。
5. 有效来源不足时自动补搜一次，仍不足则使用已有有效来源生成降级报告并明确提示。
6. 使用固定中文基准集对比原始流程与改进流程，以有效引用率作为主指标。

## 非目标

- 不实现完整界面汉化。
- 不实现拖拽式提纲编辑、提纲版本历史或多轮提纲对话。
- 不实现多个搜索引擎的动态路由。
- 不实现逐条事实真伪判断。
- 不实现无限重试；每个研究任务最多补搜一次。
- 不修改 Multi Agents 模式。

## 用户流程

### 普通模式

```text
输入问题
→ qwen-plus 直接执行研究
→ 验证并过滤来源
→ 有效来源不足时补搜一次
→ 生成快速报告
```

### 深度模式

```text
输入问题
→ qwen3.7-max 生成 3 至 5 节提纲
→ 用户查看、编辑并确认
→ 按确认后的提纲执行 Deep Research
→ 验证并过滤每轮收集的来源
→ 有效来源不足的任务补搜一次
→ qwen3.7-max 生成最终报告
```

用户取消提纲确认时不启动研究，也不产生研究费用。提纲接口失败时，页面保留原始问题并展示可重试错误，不自动绕过确认直接开始深度研究。

## 架构设计

### 1. 提纲服务

后端新增独立的提纲生成接口。接口只负责根据研究主题和报告语言返回结构化提纲，不启动搜索，也不创建后台研究任务。

请求结构：

```json
{
  "task": "研究主题",
  "language": "Chinese (Simplified)",
  "report_type": "deep"
}
```

响应结构：

```json
{
  "sections": [
    {
      "id": "section-1",
      "title": "章节标题",
      "description": "本节需要回答的问题"
    }
  ]
}
```

服务端校验章节数量为 3 至 5，每个标题和描述不能为空。模型返回无法解析时仅重试一次 JSON 解析请求，第二次失败则向前端返回明确错误。

### 2. 前端提纲确认

当 `report_type` 为 `deep` 时，提交按钮先请求提纲。页面显示章节标题和描述的可编辑列表，并提供“确认并开始研究”和“返回修改问题”两个命令。确认后，前端把最终提纲随 WebSocket `start` 消息发送给后端。

普通模式继续使用当前提交路径，不额外请求提纲。

### 3. 请求级模型配置

新增请求级 `model_profile`，避免通过全局 `.env` 切换模型：

```text
simple:
  FAST_LLM      = dashscope:qwen-plus
  SMART_LLM     = dashscope:qwen-plus
  STRATEGIC_LLM = dashscope:qwen-plus

deep:
  FAST_LLM      = dashscope:qwen-plus
  SMART_LLM     = dashscope:qwen3.7-max
  STRATEGIC_LLM = dashscope:qwen3.7-max
```

前端不允许传入任意模型名称，只发送 `simple` 或 `deep`。后端使用白名单映射生成配置，防止客户端绕过部署配置调用任意模型。Deep Research 创建子研究器时必须继续传递同一模型配置。

### 4. 提纲驱动的 Deep Research

Deep Research 收到已确认提纲后，将每个章节转换为初始研究任务，并保留章节标题用于最终报告结构。若没有提纲参数，则维持原项目行为，保证 Python 包和其他调用方兼容。

最终写作提示包含确认后的章节顺序，要求每个章节仅使用已收集上下文，并保留原始引用链接。

### 5. 来源验证

新增独立 `SourceValidator`，输入 URL 集合并返回验证结果：

```text
original_url
normalized_url
status: valid | invalid | blocked
http_status
content_length
reason
```

验证规则：

- 移除 URL fragment 和常见跟踪参数后去重。
- 使用异步 HTTP 客户端并限制并发数。
- 首先尝试 `HEAD`，不支持时回退到流式 `GET`。
- 允许正常跳转，记录最终 URL。
- HTTP 2xx 且正文长度不少于 200 字节时标记为 `valid`。
- 401、403、429 标记为 `blocked`，不计入有效来源。
- 其他错误、超时和空正文标记为 `invalid`。

默认超时为 8 秒，并发数为 5。验证结果写入研究日志，最终报告只保留有效引用。

### 6. 一次补搜策略

普通研究有效来源少于 3 个，或深度研究某一章节没有有效来源时，触发一次补搜。补搜查询由原问题、章节标题和失败原因生成，并排除已经访问的 URL。

补搜完成后再次验证新增来源。第二次仍不足时不继续循环，系统使用已有有效来源生成报告，并在日志和报告顶部标记“部分来源不足”。

## 评估设计

### 主指标

```text
有效引用率 = 有效唯一引用数 / 报告唯一引用总数 × 100%
```

“有效”必须通过同一套 `SourceValidator` 规则，Baseline 与 Enhanced 使用相同验证程序。

### 辅助指标

- 报告成功率：报告正文不少于 800 个字符，且至少包含 3 个有效唯一引用。
- 平均耗时：从研究开始到最终报告完成的秒数。
- 平均补搜次数：每个任务的实际补搜次数。
- 平均调用成本：使用项目现有 usage/cost 数据汇总。

### 对照实验

固定 10 个中文问题，覆盖科技、历史、消费趋势、教育和社会热点。每个问题保存报告类型和模型配置，Baseline 与 Enhanced 必须使用相同问题、搜索源、模型和参数。

Baseline 关闭提纲驱动、来源过滤和自动补搜；Enhanced 开启这些功能。两种模式的原始结果保存为 JSONL，汇总程序生成 CSV、JSON 和 Markdown 三种报告。

验收目标：

- 有效引用率至少提升 15 个百分点。
- 报告成功率不下降。
- 平均耗时增长不超过 30%。

目标用于验收，不作为预先承诺的结果。README 和简历只使用实际测得的数据。

## 测试策略

- 单元测试覆盖模型配置映射、提纲解析、URL 规范化、验证状态和补搜阈值。
- HTTP 验证测试使用 mock transport，不依赖公网稳定性。
- 后端集成测试覆盖普通模式直跑、深度模式提纲确认、提纲透传和最多一次补搜。
- 前端测试覆盖普通模式不显示提纲、深度模式显示并可编辑提纲、确认后发送正确 payload。
- 基准测试与产品测试分离；基准测试允许真实联网和真实模型调用，但必须记录配置与时间。
